# 多 TCG 辅助应用：项目设计与功能说明

> 本文档记录产品愿景和演进方向。当前仓库已实现本地 WS 概率计算 MVP；本文中的目录草案、候选技术和“待确认”事项不一定反映现状。实际入口、模块结构和可运行命令以根目录 `README.md`、`.agent/AGENTS.md` 及代码为准。规则假设以 `docs/ws_rule.md` 和 `docs/WS斩杀概率计算器开发计划.md` 为准。

## 1. 项目概述

### 1.1 项目名称

仓库名称：`s-tcg`。产品正式名称待维护者确定。

### 1.2 项目愿景

制作一款面向多种集换式卡牌游戏（TCG）的工具应用。项目采用可扩展设计，未来可增加不同 TCG 的专属功能；当前阶段主要聚焦 Weiß Schwarz（以下简称 WS）。当前 MVP 是 WS 斩杀概率计算器，帮助玩家根据对局状态和操作序列评估对手败北概率。工作规则记录在 `docs/ws_rule.md`；未确认的解释必须作为模型假设披露，不能描述为官方裁定。

### 1.3 设计原则

1. **面向多种 TCG**：应用整体结构应允许增加其他 TCG，不把 WS 特有规则写死在通用界面或通用数据层中。
2. **先聚焦 WS**：首阶段围绕 WS 玩家需求打磨功能，不因过早支持多个游戏而增加不必要的复杂度。
3. **结果透明**：概率计算应说明输入条件、规则假设和结果含义，避免将估算值误认为无条件的确定结论。
4. **数据与规则分离**：通用应用能力、WS 规则逻辑和卡牌数据尽量分层管理。
5. **逐步扩展**：先完成并验证 WS 斩杀概率计算器，再依据用户需求扩充 WS 功能及其他 TCG 支持。

## 2. 目标用户与使用场景

### 2.1 目标用户

- WS 玩家，尤其是需要评估对局中斩杀路线和成功概率的玩家。
- 希望使用计算、卡组分析或其他辅助工具的 TCG 玩家。
- 未来可能为其他 TCG 增加工具功能的玩家与贡献者。

### 2.2 核心使用场景

1. WS 玩家输入与斩杀计算相关的对手区域状态和我方有序操作序列（包括普通伤害与摩卡）。
2. 应用根据确认后的 WS 规则计算斩杀成功概率，并展示结果及计算条件。
3. 玩家调整输入条件，比较不同斩杀方案的概率差异。
4. 后续用户可切换 TCG，并使用该游戏专属的工具功能。

## 3. 产品范围

### 3.1 首版目标（MVP）

首版优先验证“根据对手区域状态和我方伤害序列，计算对方败北概率是否准确、易用且对玩家有帮助”，建议包含：

- 输入对方当前牌库总数/高潮数量、弃牌区总数/高潮数量、等级/时计状态、时计区高潮数量，以及我方有序操作序列（普通伤害及摩卡等卡组破坏操作）。
- 按 WS 伤害取消、牌库刷新、刷新点、时计升级和等级败北规则，计算整组伤害结算完成前对方败北的概率。
- 支持修改条件并重新计算，便于比较不同方案。
- 对输入范围、缺失状态、规则假设和不受支持的卡牌效果给出明确提示。
- 将 WS 规则与计算逻辑独立封装，为未来增加其他 TCG 留出扩展空间。
- 优先采用精确概率计算，并通过自动化测试及小牌库穷举交叉验证。

首版暂不要求：完整对战游戏、在线匹配、排名赛、账号与社交系统、卡牌交易、付费抽卡、完整卡牌数据库，以及其他 TCG 的功能支持。

### 3.2 后续迭代方向

- WS 卡组管理、卡牌检索和更多对局分析工具。
- WS 规则和卡牌资料的版本化维护。
- 用户账号、云端保存和多设备同步（确有需要时）。
- 按需求逐步增加其他 TCG 的独立工具模块。
- 管理界面、数据导入和内容维护流程。

## 4. 首个功能：WS 斩杀概率计算器

### 4.1 功能目标

根据玩家提供的对方当前区域卡牌数量与高潮数量、等级/时计状态，以及我方依序造成的伤害值，计算全部伤害结算完成前对方败北的概率，帮助玩家评估斩杀方案。首版按 `docs/ws_rule.md` 作为工作规则，并以 `docs/WS斩杀概率计算器开发计划.md` 记录规则分析、假设和实施细节。

### 4.2 待资料确认的计算要素

- 等级升级选牌策略的正式约定；时计区高潮数量为精确计算必需输入。
- 伤害过程中牌库刷新时暂存的伤害牌如何处理，以及刷新点引发升级的精确结算时点。
- “牌库耗尽且弃牌区为空”是否作为败北结果计入（当前开发计划按计入处理）。
- 首版合法伤害值、伤害序列长度及非标准构筑支持范围。
- 与正式规则核对后的精确规则版本与概率结果展示精度。

### 4.3 结果展示原则

- 清楚标明采用的规则版本和用户输入条件。
- 将概率、估算范围或模拟次数（如适用）与确定性结论区分展示。
- 对缺失数据、未实现的卡牌效果和假设条件明确告知用户。
- 输入相同的情况下，首版精确计算结果应保持一致，并能通过测试复现。

### 4.4 后续 WS 功能方向

斩杀计算器完成并验证后，再根据需求评估卡组管理、卡牌检索、其他对局计算器等功能；除已明确建模的普通伤害及摩卡查看/弃牌操作外，其他卡牌效果不属于当前首个功能范围。

## 5. 页面与交互结构

### 5.1 首版页面

1. **首页/工具首页**：显示当前支持的 TCG 与可用工具，首版突出 WS 斩杀概率计算器。
2. **WS 斩杀计算页面**：输入牌库、弃牌区、等级/时计、时计区高潮数量和操作序列；操作序列支持构造普通伤害与摩卡，并能调整顺序。
3. **规则说明区域**：查看当前采用的刷新、高潮取消、时计升级假设和规则版本。
4. **计算说明区域**：说明规则版本、输入假设、计算方式及结果限制。
5. **后续扩展入口**：新增 TCG 或工具时按模块添加，首版不要求实现。

### 5.2 交互要求

- 对无效操作给出明确原因，而不是静默失败。
- 计算结果应能对应到本次输入和规则版本，方便理解与复核。
- 输入项应随计算规则清晰分组，并提供默认值或示例（如规则允许）。
- 概率结果应易读，并能查看其对应的计算条件和限制。
- TCG 名称和规则特有术语应在中文界面中保持一致。
- 页面适配桌面浏览器和常见移动设备尺寸。
- 颜色不是区分卡牌类型和状态的唯一方式，同时使用图标或文字标识。

## 6. 技术方案

### 6.1 当前实现与后续架构方向

当前实现使用 Python 标准库 HTTP 服务、原生 HTML/CSS/JavaScript 前端和独立 Python 概率引擎。当前目录不是下方早期建议结构；贡献者应以根目录 README 项目结构为实际依据。若未来添加框架或数据持久化，应先说明需求并同步开发者文档。

- **前端**：HTML 负责页面结构，CSS 负责样式，原生 JavaScript 负责交互、页面状态和后端请求。首版可先不引入大型前端框架。
- **后端**：Python 提供 HTTP API，并负责输入校验、WS 规则计算及必要的数据读取。
- **服务框架**：可优先评估 FastAPI，以便定义接口、进行请求数据校验并生成接口说明；最终选型应结合团队熟悉程度确定。
- **数据存储**：在确认首版卡牌数据与用户数据需求后选择。若首版无需持久化用户资料，可先用版本化静态数据，避免过早引入数据库；确需持久化时可从 SQLite 起步。
- **接口格式**：前后端通过 JSON 交换数据；接口统一返回成功数据或结构化错误信息。
- **部署方式**：开发阶段本地运行；首版可将静态前端与 Python 服务部署在同一应用中，后续按规模拆分。

### 6.2 规则执行原则

- WS 专属规则和概率模型应与通用接口及页面分离，并标注规则/卡牌数据版本。
- 后端应校验计算输入的格式、范围和相互依赖条件，并对不支持的规则情形明确报错。
- 首版概率引擎应优先采用精确状态传播；若未来引入随机模拟，应独立标注误差、模拟次数和随机种子。
- 计算结果应能关联到所用输入与模型版本，便于复核和定位问题。
- 后续增加其他 TCG 时，为其提供独立的规则模块，不让 WS 假设泄漏到通用层。

### 6.3 建议目录结构

```text
项目根目录/
├── docs/                  # 中文设计、规则和接口文档
├── frontend/              # HTML、CSS、JavaScript 与静态资源
├── backend/               # Python 服务、规则引擎与数据访问
├── data/                  # 按 TCG 和版本组织的规则/卡牌数据
├── tests/                 # 概率模型、规则边界与接口测试
├── README.md              # 项目简介与启动说明
└── .gitignore             # 忽略本地环境、数据库和生成文件
```

上述目录仅是后续扩展方向，不是当前仓库布局；不要将密钥、个人数据或生产数据库文件提交到版本库。

## 7. 数据模型草案

### 7.1 TCG 模块（Game）

包含稳定的游戏标识、中文名称、规则模块版本、支持功能列表和数据版本。首版至少标识 WS；未来每种 TCG 均应拥有隔离的规则与数据命名空间。

### 7.2 卡牌数据（Card）

若斩杀计算需要卡牌资料，记录 TCG 标识、卡牌唯一编号、名称、效果所需的结构化字段、文本、数据来源和版本。字段设计以 WS 资料及实际计算需求为准，不提前假设通用效果模型。

### 7.3 计算请求与结果（Calculation）

可记录计算类型、TCG 标识、规范化输入、规则/模型版本、计算结果、计算方式及必要的模拟参数。若首版不提供历史记录功能，可仅在请求处理中使用该结构，不强制持久化。

### 7.4 规则与数据来源（Source）

记录规则或卡牌数据的来源名称、链接、版本/日期及适用范围，确保计算假设可追溯。来源信息根据用户提供的背景资料整理。

## 8. API 接口草案

接口名称和字段为初步建议，开始实现时应形成正式接口定义。

- `GET /api/games`：获取应用支持的 TCG 与可用工具。
- `POST /api/ws/lethal-calculations`：提交对手牌库/弃牌区计数、等级/时计状态、时计区高潮数量和有序操作序列（普通伤害及已实现的摩卡），返回对方败北概率及规则假设。
- `GET /api/ws/rules`：获取当前计算规则/模型版本及支持范围（是否需要此接口待实现时确认）。
- 后续按其他 TCG 的功能需要增加对应接口；通用接口不应暴露或混用不同游戏的专属规则字段。

错误响应应包含稳定的错误编号、中文可读说明和必要的上下文；不得向客户端返回密钥、堆栈或内部敏感信息。

## 9. 质量、安全与可维护性要求

- 概率计算应有自动化测试，覆盖典型输入、边界条件、非法输入、概率上下界和可复现性。
- 对计算模型的关键假设和规则版本应有文档记录；发生规则变更时应更新测试。
- 所有用户输入均需校验；未来加入账号后，对写入接口增加身份验证和权限检查。
- 对外部链接、用户提交内容和图片资源设置安全及版权审核流程。
- 记录应用错误和关键操作，但避免记录密码、访问令牌等敏感信息。
- 卡牌与规则资料应经过校验；规则改动与数据改动应具有版本记录。
- 规则更新应说明对历史计算结果和已保存数据的影响。

## 10. 开发阶段建议

### 阶段一：资料梳理与规则建模

- 接收并整理 WS 背景资料，确认斩杀定义、计算输入、规则边界和例子。
- 将计算流程转化为明确、可验证的规则说明，并列出未覆盖情况。

### 阶段二：计算原型

- 选定适合的精确计算或模拟方案，并使用资料中的例子交叉验证。
- 编写独立的 WS 计算模块和边界测试。

### 阶段三：可用 MVP

- 建立 Python API 和 HTML/JavaScript 计算界面。
- 完成输入校验、结果解释、错误提示和规则版本展示。
- 在桌面与移动端测试完整的输入、计算和结果查看流程。

### 阶段四：验证与扩展

- 使用真实使用场景验证计算结果和操作体验，修正规则遗漏。
- 按需求增加 WS 工具，并评估新增其他 TCG 的模块接口。

## 11. 首版验收标准

- 用户可以输入牌库和弃牌区的总数/高潮数、等级与时计状态、时计区高潮数量、普通伤害/摩卡混合操作序列，并获得对方败北概率。
- 计算结果符合 `ws_rule.md` 及后续确认的规则定义和测试样例。
- 无效、缺失或暂不支持的输入会被明确指出，不会返回误导性结果。
- 页面清楚展示必要的输入假设、计算方式/限制和规则版本。
- 核心概率计算有自动化测试，覆盖典型场景和边界情况。
- 首版结构保留多 TCG 扩展能力，但不要求实现 WS 以外游戏的功能。
- 项目提供中文启动说明，其他开发者可按说明在本地启动前后端。

## 12. 待确认事项

以下事项应在玩法原型阶段逐步确定：

1. 时计区高潮牌数量作为首版必需输入，及等级升级选牌策略的默认约定。
2. 伤害跨越刷新时暂存卡牌及刷新点造成时计达到 7 的具体处理时点。
3. 是否支持非标准卡组计数，以及伤害序列长度上限。
4. 是否需要保存计算记录或用户预设。
5. 首版界面视觉风格、移动端优先级和部署方式。
6. Python 服务框架及是否需要数据库。
7. 后续优先支持的其他 TCG 及其预期功能。

## 13. 文档维护约定

- 玩法、接口、数据结构或技术选型发生实质变化时，应同步更新本文档。
- 已确定的事项写入对应章节；仍有争议的事项保留在“待确认事项”中。
- 规则更新应注明版本、变更原因及对计算结果和相关数据的影响。
- TCG 专属规则、计算模型和数据来源应注明适用游戏及版本，不以通用说明替代规则验证。
